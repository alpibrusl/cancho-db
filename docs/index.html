Every write signed. Every commit checkable.

cancho-db sits in front of PostgreSQL and turns every transaction into a signed, hash-chained commit that records who wrote, under which capability, and what the statements did. Independent verifiers re-check the log, what each token allowed, and the row changes.

Try itSee how it works
a real run, replayed 
# a write goes through the proxy; each transaction is one signed commit
$ PGPASSWORD=$ADMIN psql -h 127.0.0.1 -p 5440 -U agent -d main -c "insert into people values ('ana@example.org', 'Ana Quintero')"
INSERT 0 1
$ PGPASSWORD=$ADMIN psql -h 127.0.0.1 -p 5440 -U agent -d main -c "insert into people values ('luis@example.org', 'Luis Vega')"
INSERT 0 1
# a token that can only read: the proxy refuses the statement, and PostgreSQL never sees it
$ PGPASSWORD=$READER psql -h 127.0.0.1 -p 5440 -U agent -d main -c "delete from people"
ERROR:  effect-denied: the statement was not run
$ psql -h 127.0.0.1 -p 5532 -U postgres -d site_demo -At -c "select count(*) from people"   # straight to PostgreSQL: nothing was deleted
2
# erase a person: the row, the capture's copies of it, and every statement that names her
$ PGPASSWORD=$ADMIN psql -h 127.0.0.1 -p 5440 -U agent -d main -c "select cancho_erase('people', '[\"ana@example.org\"]')"
erased: 1 row(s) deleted, 2 delta row(s) scrubbed
$ grep -c ana@example.org log/log log/tokens log/stmts
log/log:0
log/tokens:0
log/stmts:0
$ grep -c luis@example.org log/stmts   # another subject's statement is still there
1
# then anyone can check the log, with nothing but the log directory and the root key
$ verify log/log --root $ROOT --tokens log/tokens --stmts log/stmts
ok commits=3 branches=1 level=2+ir

Recorded from real runs of the proxy, psql and the verifier on one machine, trimmed to what fits here (the file names are shortened; the proxy ran on port 5440 in front of PostgreSQL on 5532). It is not a live session. $ADMIN and $READER are capability tokens made with tools/mint.py: the first may read, write and call cancho_erase, the second may only read.

What it gives you

Not a promise that the database behaved: a log that a stranger can check, and a list of what that check does not cover.

🔗

Signed, chained commits

Every transaction is one commit in an append-only log, signed with Ed25519 and chained by SHA-256. A verifier needs only those two functions to say whether the log is intact, in order and not cut short (L1).

🔑

Authority, checked twice

A capability token can only narrow. The proxy checks each statement against it before PostgreSQL sees it, and a verifier re-derives what the recorded statements do and compares it with what the commit says (L2).

⏲

Replayable data

Triggers capture every row change. A verifier replays them and checks that the tables hold exactly what the log says they should (L3a).

🌿

Branches, AS OF and merge

cancho_fork gives an agent its own branch; AS OF reads a table as a commit left it; cancho_merge is a checked three-way merge, or nothing if there is a conflict.

🚫

Erasure that still verifies

cancho_erase deletes a person's rows and what the capture kept of them, and rewrites the statements that name them. Hashes and commitments stay, so the log still verifies.

📑

Honest about its limits

Every claim has a row saying what it rests on and what it does not show. A refusal always carries a rule tag.

How it works

A proxy in front of an ordinary PostgreSQL. Agents connect with a token as the password; whatever the proxy writes, the verifiers check.

The three verifiers are one in cancho, one in Python and one in Go that a separate agent session wrote from the specs alone; they must agree on every golden vector. What that does and does not show is in claims.md.

Measured, not promised

467golden vectors, one tampered or refused case for each rule
3verifiers that agree on every one
827deliberate faults, each of which must make a check fail
143claims, each with what it rests on and what it does not show

These counts are written into this page by scripts/site.py from the repository, and scripts/check.sh fails if they are stale. A count says how much is checked, not that nothing is missing; the next section says what is.

What it is not, yet

  • A proxy, not a database. It runs in front of PostgreSQL, which still stores the data; its own storage engine (M3) is not started. The upstream role must be allowed to create triggers and event triggers, and every table needs a primary key.
  • A SQL subset. No subqueries, CTEs, set operations or window functions, and a closed set of DDL. A statement outside it is refused with a rule tag, never run.
  • Values bound by a client are not recorded (L3b is not built), and snapshots are not built.
  • Erasure has edges. It is by table and key; a subject who appears in other statements only in other forms, or by a number, is found by an offline tool, not by the key. PostgreSQL's own storage and any copy made outside the system are not wiped.
  • One commit at a time, loopback clients only, and every commit costs a signature: the proxy is much slower per statement than PostgreSQL alone. The measurements are in m1-commit-path.md.
  • A working name. The claims page lists every claim and what each one leaves out.

Try it

Check a log first: you need the cancho compiler, or just Python, and nothing else.

git clone https://github.com/alpibrusl/cancho-db && cd cancho-db
cancho build --std src/commit.cho src/verify.cho -o verify    # or: python3 tools/verify.py, the same arguments
./verify vectors/ok_chain3.log
ok commits=3 branches=1
./verify vectors/seq_skips.log
reject rule=seq-gap record=1

Then put the proxy in front of a PostgreSQL you can throw away:

proxy 5440 127.0.0.1 5432 main $ROOT postgres postgres ./log ./signing.key
PGPASSWORD=$(python3 tools/mint.py password) psql -h 127.0.0.1 -p 5440 -U agent -d main -c 'select 1'
build/verify log/log --root $ROOT --tokens log/tokens --stmts log/stmts

The README has the build line for the proxy, the arguments, and what tools/mint.py mints. The gates are run by sh scripts/check.sh, against a real PostgreSQL.
