Every write signed. Every commit checkable.

cancho-db is a database with its own storage engine behind PostgreSQL's protocol. Every transaction is a signed, hash-chained commit that records who wrote, under which capability, and what the statements did, and independent verifiers re-check the log, what each token allowed, and the rows.

# a token that may only read: the statement is refused before it runs
$ PGPASSWORD=$READER psql -c "delete from people"
ERROR:  cancho-db: refused effect-denied
# a person goes, and her visits with her
$ psql -c "delete from people where email = 'ana@example.org'"

$ psql -At -c "select who from visits"
luis@example.org

$ build/logexport pages log > log; build/logexport pages tokens > tokens; build/logexport pages stmts > stmts
$ python3 tools/verify.py log --root $(cat root.pub) --tokens tokens --stmts stmts

What it gives you

Not a promise that the database behaved: a log that a stranger can check, and a list of what that check does not cover.

🔗

Signed, chained commits

Every transaction is one commit in an append-only log, signed with Ed25519 and chained by SHA-256. A verifier needs only those two functions to say whether the log is intact, in order and not cut short (L1).

🔑

Authority, checked twice

A capability token can only narrow. Each statement is checked against it before it runs, and a verifier re-derives what the recorded statements do and compares it with what the commit says (L2).

⏲

Replayable data

Each commit carries the row changes it made. A verifier replays them and checks that the tables hold exactly what the log says they should (L3a).

🌿

History you can read

AS OF reads a table as a commit left it, a fork gives an agent its own branch, and transactions can run side by side, the loser refused rather than merged wrongly.

🚫

Erasure that still verifies

An erase removes a row and every past version of it from the file. Salted hashes and commitments stay, so the log still verifies.

📑

Honest about its limits

Every claim has a row saying what it rests on and what it does not show. A statement outside what it does is refused with a rule tag, never run some other way.

How it works

One server, no PostgreSQL behind it. Clients connect with a token as the password; whatever the engine commits, the verifiers check.

The three verifiers are one in cancho, one in Python and one in Go that a separate agent session wrote from the specs alone; they must agree on every golden vector. The same log is written by a proxy that sits in front of a stock PostgreSQL instead (the first form, still kept). What that does and does not show is in claims.md.

Where it is

Each step is done when a test says so, not on a date.

  • The specs and three verifiers: built. The commit and log format, capability tokens, the statement IR and the row facts, with golden vectors.
  • The proxy in front of PostgreSQL: built. psql and five drivers; branches, AS OF, merge, replay, erasure.
  • The engine: built and served. A crash-tested copy-on-write B+tree with the log inside it, and PostgreSQL's protocol, simple and extended. It serves TLS, clients from other machines with a login, up to 128 connections, and transactions side by side. SQL with joins, aggregates, indexes, times, returning, check constraints and references with cascade. Each statement is answered as PostgreSQL answers it or refused with a rule tag.
  • Real clients on it: started. cancho-hooks runs on the engine and passes 43 checks across the 11 scenarios of its own history test. cancho-ota applies 45 of its 49 migration statements as written; 55 of its 134 queries run so far.

Measured, not promised

467golden vectors, one tampered or refused case for each rule
3verifiers that agree on every one
1,903deliberate faults, each of which must make a test fail
226claims, each with what it rests on and what it does not show

These counts are written into this page by scripts/site.py from the repository, and scripts/check.sh fails if they are stale. The engine is held to PostgreSQL by random histories and fixed statements on every change, to crash and failing-fsync tests, and to a soak under kills. A count says how much is checked, not that nothing is missing; the next section says what is.

What it is not, yet

  • A SQL subset. No subqueries in from, CTEs, set operations or window functions; no on conflict do update. A statement outside the subset is refused with a rule tag, never run some other way.
  • Not a way to move a database off PostgreSQL yet. The engine serves a database it was given from the start; the shadow run that would take one over from PostgreSQL is designed and not built, and neither is merge on the engine.
  • Not fast. Every commit is signed: on the test disk a commit's file writes cost about 0.6 ms and its signature 3.8 ms.
  • Values bound by a client are not recorded (L3b is not built), and snapshots are not built.
  • Erasure has edges. It is by table and key; a copy made outside the system, or a backup, is not wiped.
  • A working name. The claims page lists every claim and what each one leaves out.

Try it

Check a log first: you need the cancho compiler, or just Python, and nothing else.

git clone https://github.com/alpibrusl/cancho-db && cd cancho-db
cancho build --std src/commit.cho src/verify.cho -o verify    # or: python3 tools/verify.py, the same arguments
./verify vectors/ok_chain3.log
ok commits=3 branches=1
./verify vectors/seq_skips.log
reject rule=seq-gap record=1

Then run the engine and talk to it with psql:

sh scripts/check.sh checks                      # builds build/engine and build/logexport, and runs the tests
build/engine pages 5450 signing.key root.pub    # page file, port, the log's signing seed, the token root
PGPASSWORD=$(python3 tools/mint.py password --effects 'r:*,w:*,d:*,c:*,n:*') psql -h 127.0.0.1 -p 5450 -U agent -d main

The README has the options (tls=, places=), how to read the log out and verify it, and the proxy for a stock PostgreSQL. tools/mint.py makes tokens for test keys only.
